# 실제 기술 발표에서 먼저 확인할 문제

짧은 예제가 보기 좋다고 긴 코드와 실제 화면이 있는 발표에도 같은 배치가 맞는 것은 아닙니다. 디자인 피드백이 오면 원본 전체를 먼저 렌더해 보고, 색 수정 전에 정보의 크기와 읽는 순서를 다시 설계합니다.

## 우선순위

1. 표지는 제목·부제·발표 정보만 기본으로 둡니다. 개요, 기능 3개, 수치와 목차를 자동으로 넣지 않습니다. [기본 표지](../templates/cover-minimal.json)를 먼저 확인합니다. 다른 예제의 정보 패널은 본문 개요로 취급합니다.
2. 주제색을 화면 전체에 칠하지 않습니다. 포인트색은 중요한 변화나 결론에 배정합니다. 채도를 유지하라는 명시 요청이 없다면 밝은 중립 바탕과 작은 강조 영역부터 검토합니다.
3. 의미를 설명할 수 없는 가장자리 띠, 점, 진행 표시, 반복 영문 라벨은 제거합니다. 실제 목차 이동에 쓰는 레일은 유지할 수 있습니다.
4. 비교표는 `분류 → 기존 → 개선` 순서처럼 눈이 한 방향으로 움직이도록 배치합니다. 분류 열을 중간에 끼워 넣거나 모든 셀에 배경색을 넣지 않습니다. 숫자 표의 경우 단위와 숫자 열 정렬을 별도로 확인합니다.
5. 코드와 복잡한 그래프가 한 장에서 경쟁하면 분리합니다. 그래프는 주요 흐름과 실패 경로가 읽히는 면적을 확보하고, 코드는 설명할 구간을 따로 보여 줍니다. 생략한 원문은 노트나 별도 코드 페이지에 보존하고 생략 사실을 알립니다.
6. 실제 실행 캡처가 핵심이면 캡처를 크게 배치합니다. 작은 전체 화면 옆에 내용을 다시 써 놓는 것만으로 근거가 읽힌다고 판단하지 않습니다. 읽을 부분을 자르고, 필요하면 전체 화면은 부록에 둡니다.

## 실제 결과로 검수

표지, 가장 복잡한 본문, 실행 화면을 먼저 만듭니다. 쉬운 표지와 짧은 예제만 검사한 뒤 전체에 적용하지 않습니다. 같은 크기의 원본과 수정본을 놓고 무엇이 먼저 읽히는지 비교합니다.

- 중요한 정보가 장식보다 먼저 보이는가?
- 도식과 코드의 글자가 실제 발표 화면에서 읽히는가?
- 화살표가 시작·도착 노드에 연결되고 실패 조건도 보이는가?
- 표의 한 행을 왼쪽부터 읽었을 때 비교 관계가 분명한가?
- 정보가 적은 장의 빈 공간과 복잡한 장의 밀도가 발표 흐름에 맞는가?

자동 검사는 잘림과 겹침을 찾는 보조 수단입니다. 오류 0건, 시안 개수, 리뷰어 수로 미적 완성도를 주장하지 않습니다. 피드백받은 개인 자료는 허락 없이 공개 스킬의 예제로 배포하지 않습니다.
